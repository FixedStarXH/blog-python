# Blog System Python 目标架构与目录设计

## 1. 架构决策

- **Web 框架**：FastAPI，路由层只做 HTTP 解析、Schema 校验、权限依赖和响应映射。
- **数据库**：SQLAlchemy 2.x，先使用同步 Session 与同步 Repository，避免在同步 MySQL 驱动上混用 async；确有异步数据库驱动需求时另行评估。
- **迁移**：Alembic 管理 schema 版本和从 Go 数据导入的迁移脚本。
- **缓存/队列**：Redis 用于缓存、限流、refresh token、AI 配额及浏览量缓冲；定时发布、视图量刷库和 RAG 重建进入独立任务模块，任务执行方式集中管理。
- **前端**：保留当前 `web/` React/Vite MPA，通过 Docker Node 构建阶段输出 `dist/`，Python API 托管构建产物。
- **AI 集成**：Chat 和 Embedding 客户端分离，统一超时、错误归类、重试策略和可观测日志；RAG 服务不直接依赖 FastAPI Request。

## 2. 分层和依赖方向

```text
HTTP Router
    ↓
Schema + Dependency（输入输出、身份和权限）
    ↓
Service（用例、事务边界、状态转换）
    ↓
Repository / Cache / Integration（数据与外部服务）
    ↓
SQLAlchemy Models / MySQL / Redis / AI Provider / 文件系统
```

依赖只向下流动。Service 不导入 FastAPI；Repository 不决定 HTTP 状态码；Pydantic Schema 不充当 SQLAlchemy ORM 模型。跨 Repository 的写入事务由 Service 明确控制。

## 4. 模块责任

### API 路由

路由必须保持 Go 项目中的 URL 和 HTTP 方法。复杂响应通过 Schema 显式定义。兼容层只负责字段别名、旧路径映射和 `{code,message,data}` 信封，不允许把业务逻辑塞进通用 middleware。

### Schema

- 请求 Schema 处理 camelCase 输入和长度/枚举校验。
- 响应 Schema 控制字段暴露，尤其禁止输出密码、refresh token、Embedding 向量和私有文章正文。
- SQLAlchemy 对象不能直接序列化成 API 响应。

### Service

每个用例有清晰事务边界，例如审核发布、批量评论审核、refresh 轮换、文章更新与索引排队。状态转换必须显式验证前置状态，避免非法重复审核或重复发布。

### Repository

只处理持久化查询与写入，包括软删除过滤、分页计数、标签关联和带锁查询。公共文章查询默认限定 `status=published`、`deleted_at IS NULL`、非私密。

### Cache 与任务

缓存 key 包含所有影响结果的筛选条件。文章变更统一调用缓存失效入口。view 计数缓冲写入 Redis 并由任务批量刷库；任务重试必须幂等。Redis 不可用时各功能按需求文档降级。

### RAG

索引流程：公开文章读取 → 清理 HTML → 分块 → 调用 Embedding → 校验数量、维度和模型 → 单事务替换旧索引。检索流程先限定公开文章，再做向量相似度排序。文章状态变化后通过任务模块重建或删除索引。

## 5. 数据表建议

保持 Go 领域实体名称和关系，按 SQLAlchemy 规范映射：

- `users`：用户名/邮箱与 `deleted_at` 组成可复用的唯一约束；密码哈希、角色、启用状态。
- `articles`：作者、分类、可空专栏、状态、审核原因、发布时间、私密密码、计数及软删除时间。
- `categories`、`tags`、`article_tags`、`columns`：名称、排序、专栏作者和多对多关联。
- `comments`：文章、可空用户、昵称、父评论、审核状态和点赞数。
- `article_views`、`article_likes`：用户/IP 去重记录，约束粒度与原 Go 实现一致。
- `settings`、`links`、`images`：站点 KV、公开状态友链和图库元信息。
- `article_chunks`：块序号、内容、向量二进制/JSON、Embedding 模型、维度、内容哈希、索引时间。
- `audit_logs`、`refresh_tokens`：安全审计与 refresh token 轮换/撤销。

唯一索引、软删除和计数约束均由 Alembic migration 显式维护，避免以 ORM 自动建表代替升级策略。

## 6. 迁移顺序

1. **基线**：固定 Go API 契约、状态常量、数据库字段和前端请求样例；确定 Python 运行与配置方式。
2. **基础设施**：设置、SQLAlchemy、Alembic、统一错误、日志、响应 envelope、健康探针。
3. **身份与权限**：用户、密码哈希、双 token 轮换、角色依赖、审计和限流。
4. **CMS 主流程**：文章/分类/标签/专栏/评论、软删除、审核状态和 API 兼容。
5. **运营功能**：上传图库、友链、设置、仪表盘、归档、RSS、Sitemap。
6. **运行能力**：Redis 缓存和计数任务、优雅关闭、Compose 与静态前端托管。
7. **AI/RAG**：摘要/润色、事务索引、重试、受限检索、SSE、多轮历史和成本控制。
8. **数据迁移与切换**：离线导入 Go 数据、比对记录数和关联、执行接口契约验收，再决定切换。

每阶段先补齐相应模块和数据迁移，再进入下一阶段；不得继续把所有职责累积进 `app/main.py`。

## 7. 当前 Python 目录与目标的差距

当前 Python 项目已有 Alembic、独立路由、ORM、部分 Repository/Service、RAG 和任务模块，`app/main.py` 主要负责应用装配与中间件。设置、友链、部分后台管理和 AI 用例仍在路由中直接处理业务与事务，输入输出模型也未完全细化。第 12 步将按用例继续分层，具体任务见[未完成工作详细清单](未完成工作详细清单.md)。
